Rules, Custom Modes וסטנדרטיזציה

כללים עקביים לכל הפרויקט

מטרת הפרק

בסוף הפרק: כללים עקביים לכל הפרויקט

מבוא

Rules = התנהגות קבועה של Bob. Custom Modes = תפקידים (Reviewer, Planner). סטנדרט = פחות variance בין sessions. מבנה: .bob/rules/ לכל המצבים, .bob/rules-code/ / rules-plan/ / rules-ask/ לכל מצב.

מושגי מפתח

רחפו מעל שם המושג (או לחצו במסך מגע) לפירוט: מבוא, משמעות וכוונה.

Rules

מבוא

בלי כללים קבועים כל שיחה מתחילה מאפס. Rules הם התנהגות גלובלית של Bob.

משמעות

הוראות קצרות שחלות תמיד: שפה, בדיקות חובה, סגנון commit, מה לא לגעת.

כוונה

הכוונה: מעט כללים שניתנים לבדיקה. מאה כללים סותרים מתעלמים מהם.

הוראות ב-.bob/rules/ — חלות על כל המצבים.

דוגמה: עברית בתגובות
זהירות: 100 rules — conflict.

Custom Mode

מבוא

לא כל משימה צריכה את אותו Bob. Custom Mode הוא תפקיד עם הרשאות.

משמעות

מצב מותאם: למשל Reviewer שרק קורא ומעיר, או Planner בלי עריכה.

כוונה

הכוונה: להגדיר תפקיד + scope. שם בלי גבולות הוא קישוט.

persona + הרשאות.

דוגמה: Reviewer: read + comment
זהירות: mode בלי מטרה.

Convention

מבוא

שני סגנונות באותו פרויקט עולים בזמן review. Convention מיישר קו.

משמעות

הסכמה על שמות, מבנה תיקיות, פורמט, ושפה — כדי ש-Bob לא ימציא סגנון.

כוונה

הכוונה: לכתוב conventions ב-AGENTS.md ולדרוש עמידה בהם ב-Plan.

סגנון קוד אחיד.

דוגמה: camelCase JS
זהירות: Bob ממציא סגנון.

Drift

מבוא

הכללים נכתבו בינואר. באפריל ה-stack השתנה. Drift הוא הפער.

משמעות

סטייה בין מה שכתוב ב-rules/AGENTS לבין איך באמת עובדים בקוד.

כוונה

הכוונה: לבדוק drift אחרי שינוי משמעותי, ולעדכן מסמכים לפני שהם מכשילים.

סטייה מהכללים.

דוגמה: rules לא מעודכנות
זהירות: ignore drift.

Rule Quality

מבוא

המושג Rule Quality הוא אחד מאבני הבניין של הפרק.

משמעות

Rule טוב = ניתן לבדיקה, חל על כל session, לא סותר rule אחר.

כוונה

הכוונה: להבין מתי להשתמש בו, ומה משתבש אם מתעלמים — Rule ש-Bob לא יכול לאכוף — כתוב קוד נקי = לא testable ולא אכיף.

דוגמה: כל Agent iteration מסתיים ב-pytest — ניתן לבדוק
זהירות: Rule ש-Bob לא יכול לאכוף — כתוב קוד נקי = לא testable ולא אכיף.

Mode-specific Rules

מבוא

המושג Mode-specific Rules הוא אחד מאבני הבניין של הפרק.

משמעות

Rules שחלות רק ב-mode מסוים: .bob/rules-code/, rules-plan/, rules-ask/.

כוונה

הכוונה: להבין מתי להשתמש בו, ומה משתבש אם מתעלמים — לשים rules ספציפיות ל-Agent ב-.bob/rules/ הכללי — חלות גם ב-Ask ומבלבלות.

Rules שחלות רק ב-mode מסוים: .bob/rules-code/, rules-plan/, rules-ask/.

דוגמה: rules-code: הרץ tests לפני done. rules-ask: תמיד cite source.
זהירות: לשים rules ספציפיות ל-Agent ב-.bob/rules/ הכללי — חלות גם ב-Ask ומבלבלות.
משל מהעולם האמיתי

Rules הן הגדרות התנהגות קבועות שחוסכות הוראות חוזרות בכל prompt. בלי rules — Bob ממציא סגנון, בוחר שפה ומחליט על convention בכל שיחה. יותר מ-10–15 rules מסותרות פוגעות: Bob מתעלם ממה שקבור בסוף הרשימה.

שאלות לחשיבה: כתבו rule אחד ל-TaskFlow שיחסוך לכם הוראה חוזרת. בדקו: האם ה-rule testable? האם Bob יודע מתי הוא הפר אותו?

עבודה עם IBM Bob
Plan

Rules קצרות, focused.

Prompt לדוגמה

Propose 5 rules for TaskFlow covering tests, commits, and scope. Do not create files yet.

למה זה עובד: Plan rules — לא spam.

טעות נפוצה

לא: 20 rules — ביניהן כתוב קוד מסודר ו-תמיד תסביר מה עשית. Bob מתעלם מהרשימה כולה.

כן: 5 rules מדידות: Run pytest before done, No new Python packages without Ask first, Scope to named files only.

מעבדה מודרכת
  1. כתבו 3 rules מדידות ל-TaskFlow.
  2. הניחו rule שBob יפר — בדקו האם הוא מציין זאת.
  3. עדכנו rule שלא עבד.
  4. commitו rules עם הסבר למה כל rule נוספה.
  5. הצלחה = כל rule שלכם ניתנת לבדיקה: אפשר לאמר כן/לא — הRule הושמר.

תשובה לדוגמה: עדכון rules כש-stack משתנה.

תשובה לדוגמה: Bob מתעלם ממנה או מפרש לפי שיקול דעתו. Rule חייבת להיות בינארית — הושמרה / לא הושמרה.
מה ההבדל בין .bob/rules/ לבין .bob/rules-code/?
תשובה לדוגמה: rules/ = חל על כל mode. rules-code/ = רק ב-Agent/Code mode. rules שמוגבלות ל-Agent לא צריכות לטעון ב-Ask.
