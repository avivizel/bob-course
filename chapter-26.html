Validation vs Parameterization

מבוא

המושג Validation vs Parameterization הוא אחד מאבני הבניין של הפרק.

משמעות

Validation בודק אם הקלט חוקי עסקי (למשל priority ∈ {low, medium, high}). Parameterization מונע הזרקת קוד (כמו SQL Injection) ע'י הפרדת נתונים מפקודות בשרת.

כוונה

הכוונה: להבין מתי להשתמש בו, ומה משתבש אם מתעלמים — להניח שאימות בלבד (sanitize) מונע הזרקות מבלי להשתמש בפרמטריזציה.

Security Headers

המושג Security Headers הוא אחד מאבני הבניין של הפרק.

משמעות

הגדרות הגנה בדפדפן (כגון CSP, HSTS, X-Content-Type-Options ו-secure cookie attributes). ב-Flask ניתן להגדיר headers ישירות או באמצעות extension מתאים, אך יש לבדוק את תיעוד הגרסה שבה משתמש הפרויקט.

כוונה

הכוונה: להבין מתי להשתמש בו, ומה משתבש אם מתעלמים — חוסר שימוש ב-Security Headers.

AI Security Threats

מבוא

המושג AI Security Threats הוא אחד מאבני הבניין של הפרק.

משמעות

איומי אבטחה ייחודיים ל-AI: Prompt Injection (הזרקת פקודות), Excessive Agency (אוטונומיה מוגזמת), Over-privileged Tools (כלים בעלי הרשאות יתר), Sensitive Context Leakage (דליפת מידע רגיש מה-Context) וקוד לא בטוח שנוצר ע'י המודל.

כוונה

הכוונה: להבין מתי להשתמש בו, ומה משתבש אם מתעלמים — סמיכה עיוורת על סוכן AI ללא גבולות אבטחה ו-Least Privilege.

איומי אבטחה ייחודיים ל-AI: Prompt Injection (הזרקת פקודות), Excessive Agency (אוטונומיה מוגזמת), Over-privileged Tools (כלים בעלי הרשאות יתר), Sensitive Context Leakage (דליפת מידע רגיש מה-Context) וקוד לא בטוח שנוצר ע'י המודל.

דוגמה: דליפת API_KEY דרך prompt או הפעלת כלי הרסני
זהירות: סמיכה עיוורת על סוכן AI ללא גבולות אבטחה ו-Least Privilege.
משל מהעולם האמיתי

אבטחה שנוספת בסוף הפרויקט מחייבת refactor — headers, validation ו-secrets management שלא תוכננו מראש. Threat model שנכתב ב-PRD הופך כל feature request לשאלת אבטחה: מה התוקף יכול לעשות עם זה? — לפני שכותבים שורה. ב-RAVEN של security חשוב במיוחד לבדוק Assumptions על trust boundaries, Effects על attack surface, ו-No-go כמו אין secrets בקוד.

שאלות לחשיבה: זהו את ה-Threat #1 של TaskFlow בהגדרת STRIDE: כתבו Asset, Threat ו-Mitigation אחת. לאחר מכן הוסיפו RAVEN security review: מה הנחתם על trust boundary, מה ה-attack surface שהושפע, ומה אסור שישתנה?

עצור והחלט
תרחיש: Bob מציע להוסיף fallback hardcoded API key בקוד כדי לא לשבור את ה-demo בpresentation.
עצור והחלט — מה עושים?
דוחים. Hardcoded API key בקוד = secret בגיט = בעיית אבטחה קריטית גם ב-demo. הדרך הנכונה: .env עם API_KEY=demo_placeholder + הוראת README לsetup. Demo key שנחשף ב-repo יכול להיות scraped ולעלות כסף או לגרום נזק. לא לשבור demo אינו סיבה מספקת — Security headers are not negotiable.
מעבדה מודרכת
  1. Threat model הכולל איומי OWASP ואיומי AI ייחודיים.
  2. RAVEN security review: Assumptions / Effects / No-go.
  3. Fix 1 finding.
  4. Secret scan.
  5. Security Headers check (CSP, HSTS).
  6. הצלחה = threat model עם STRIDE lite ואיומי AI, לפחות finding אחת תוקנה, secret scan נקי, Security Headers (כגון CSP) מוגדרים, ו-No-go כמו אין secrets בקוד נשמר.
