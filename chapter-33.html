מטרת הפרק

בסוף הפרק: מה עובר על הקו, איפה המודלים רצים, ואיך להגן על IP

מבוא

Bob SaaS מבוסס על ארכיטקטורה מבוזרת הפרוסה במספר אזורים בענן, ומחברת את ה-Client בצורה מאובטחת לשירותי ה-inference. הבנת ה-Data Flow חיונית כדי להבטיח עמידה בכללי אבטחת מידע וסוברניות נתונים (Data Residency). * הארכיטקטורה המוצגת בפרק זה היא מופשטת ונועדה להמחשת ה-data flow בלבד (Illustrative / not a contractual architecture; רכיבי ה-implementation בפועל עשויים להשתנות).

Regional Deployment ו-Data Residency

משמעות

SaaS deployment אזורי המאפשר לארגונים לנתב את התעבורה והפניות שלהם לאזורים גאוגרפיים מוגדרים (כגון ארה"ב, אירופה או יפן) בהתאם לדרישות ה-data residency והרגולציה המקומית.

Bob Model Gateway

מבוא

המושג Bob Model Gateway הוא אחד מאבני הבניין של הפרק.

משמעות

שכבת routing קונספטואלית בין ה-Client ל-LLMs. מטפלת ב-AuthZ, Metering, feature flags ו-audit. הוא לא ה-LLM עצמו — הוא ה-broker שמנתב לכל מודל.

כוונה

הכוונה: להבין מתי להשתמש בו, ומה משתבש אם מתעלמים — לבלבל בין Bob Model Gateway (שכבת ניתוב) לבין ה-LLM עצמו.

מה עובר על הקו ו-.bobignore

מבוא

המושג מה עובר על הקו ו-.bobignore הוא אחד מאבני הבניין של הפרק.

משמעות

בכל בקשה נשלח רק ה-inference payload המכיל את ה-prompts, קטעי קוד שצורפו במפורש (ע'י @) ופלט ה-terminal. הקובץ .bobignore הוא מנגנון לצמצום ה-context והגישה של Bob לקבצים רגישים בפרויקט.

כוונה

הכוונה: להבין מתי להשתמש בו, ומה משתבש אם מתעלמים — הנחה ש-.bobignore הוא פתרון אבטחה מוחלט — יש להשתמש בו לצמצום קונטקסט אך לא כתחליף ל-secrets management, בקרת גישה (access control) או data governance ארגוני.

AuthN + AuthZ

מבוא

המושג AuthN + AuthZ הוא אחד מאבני הבניין של הפרק.

משמעות

AuthN = SSO / API key. AuthZ = הרשאות per-tool ב-Harness. Metering = מדידת token usage לחיוב ו-governance.

כוונה

הכוונה: להבין מתי להשתמש בו, ומה משתבש אם מתעלמים — לחשוב שRules ב-AGENTS.md = security enforcement. הם הכוונה — AuthZ ב-Harness היא האכיפה.

דוגמה: SSO ארגוני → Bob IDE → Harness מחליט אילו כלים מותרים → LLM inference → audit log
זהירות: לחשוב שRules ב-AGENTS.md = security enforcement. הם הכוונה — AuthZ ב-Harness היא האכיפה.

On-Prem / Air-Gap

מבוא

המושג On-Prem / Air-Gap הוא אחד מאבני הבניין של הפרק.

משמעות

אותה ארכיטקטורה מנטלית — endpoint inference הוא watsonx.ai פנימי (OpenShift) במקום inference בענן. תמונות קונטיינר מ-private registry. prompts לא עוזבים את הרשת הארגונית.

כוונה

הכוונה: להבין מתי להשתמש בו, ומה משתבש אם מתעלמים — לחשוב ש-air-gap = פחות יכולות. אותה לולאה, endpoint פנימי בלבד.

אותה ארכיטקטורה מנטלית — endpoint inference הוא watsonx.ai פנימי (OpenShift) במקום inference בענן. תמונות קונטיינר מ-private registry. prompts לא עוזבים את הרשת הארגונית.

דוגמה: Bob IDE → enterprise Harness → watsonx.ai GPU nodes (OpenShift) — NO public egress
זהירות: לחשוב ש-air-gap = פחות יכולות. אותה לולאה, endpoint פנימי בלבד.
משל מהעולם האמיתי

Bob שולח רק מה שנמצא בinference payload — קבצים שצורפו ב-@, טקסט שנכתב בprompt, ו-terminal output שנוסף. קוד שיושב בדיסק אבל לא צורף לא יוצא. .bobignore הוא ההגדרה המפורשת של לא לשלוח — בלי .bobignore, מידע רגיש עלול להגיע ל-LLM בלי כוונה דרך @ רחב.

שאלות לחשיבה: עבור הפרויקט שלכם: איזה אזור נכון? איזה מודל? מה ב-.bobignore? מי מנהל את ה-AuthZ?

מעבדה מודרכת
  1. בדקו .bobignore — ודאו .env, secrets, *.pem חסומים.
  2. Ask: בקשו מBob לרשום מה יישלח ל-LLM אם תצרפו @src/.
  3. זהו את ה-region שהארגון שלכם משתמש בו — EU/US/JP.
  4. בדקו שה-AuthZ settings מגבילים כלים מסוכנים (rm, deploy).
