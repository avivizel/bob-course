Debugging שיטתי עם Bob

סיבה אמיתית — לא ניחוש

מטרת הפרק

בסוף הפרק: סיבה אמיתית — לא ניחוש

מבוא

Debug = reproduce → isolate → hypothesis → test. Bob מ accelerate — לא מחליף method. מודל RAVEN מסייע להתמקד בהנחות השגויות, בדרכי האימות, ובמניעת תופעות לוואי.

מושגי מפתח

רחפו מעל שם המושג (או לחצו במסך מגע) לפירוט: מבוא, משמעות וכוונה.

Reproduce

מבוא

באג שאי אפשר לשחזר אי אפשר להוכיח שתוקן.

משמעות

אותם צעדים, אותה סביבה, אותה תוצאה שגויה — תיעוד מדויק.

כוונה

הכוונה: לא לבקש מ-Bob תתקן לפני שיש תרחיש שחזור.

same steps → same bug.

דוגמה: add task twice
זהירות: can't reproduce.

Isolate

מבוא

תיקון במסך כשהבעיה ב-API מבזבז זמן. Isolate מצמצם שכבה.

משמעות

לקבוע אם התקלה ב-UI, ב-API, ב-DB או ברשת — לפני שינוי קוד.

כוונה

הכוונה: לשאול באיזו שכבה זה נשבר במקום לשנות באקראי.

narrow layer.

דוגמה: API vs UI
זהירות: fix symptom.

Hypothesis

מבוא

ניחוש לא מנוסח מוביל לשינויים אקראיים. Hypothesis אפשר לבדוק.

משמעות

טענה שניתנת להפרכה: לחיצה כפולה שולחת POST פעמיים.

כוונה

הכוונה: לבקש מ-Bob 3 השערות ואיך לבדוק כל אחת — בלי לגעת בקוד עדיין.

testable guess.

דוגמה: race on double submit
זהירות: random changes.

Evidence

מבוא

תיקון בלי הוכחה הוא תקווה. Evidence הוא לוג, network, breakpoint.

משמעות

נתון שתומך או מפריך השערה: קונסול, כרטיסיית רשת, סטטוס, stack trace.

כוונה

הכוונה: לא למזג תיקון בלי ראיה שההשערה הייתה נכונה.

logs, breakpoints.

דוגמה: console + network tab
זהירות: fix without proof.

RAVEN Debugging

מבוא

שימוש במודל RAVEN לצורך פתרון באגים וחקירת תקלות.

משמעות

Assumptions (אילו הנחות שגויות עשינו?), Verification (כיצד נוכיח שהבאג נפתר בבדיקה מדויקת?), Effects (אילו מערכות קצה או לוגיקה עלולות להיפגע מהתיקון המקומי).

כוונה

הכוונה: למנוע תיקונים חפוזים שרק מטפלים בסימפטום ויוצרים באגים חדשים.

שימוש ב-RAVEN לזיהוי הנחות שגויות (Assumptions), הגדרת ראיות אימות לתיקון (Verification), ומיפוי השפעות הקוד על רכיבים אחרים (Effects).

דוגמה: בדיקה אם שינוי שאילתה משפיע על APIs אחרים.
זהירות: תיקון מקומי שיוצר באג במקום אחר מבלי לבחון Effects.
משל מהעולם האמיתי

תתקן בלי reproduce steps נותן ל-Bob תוצר שנראה נכון — עד שהבאג מתרחש שוב. Hypothesis testable מכוונת את Bob לאסוף logs ספציפיים, לא לשנות קוד באקראי. שינוי קוד לפני ראיה הוא debugging בהנחה, לא בבדיקה.

שאלות לחשיבה: כתבו bug report ל-TaskFlow: reproduce steps (3 שלבים), expected vs actual, ו-hypothesis אחת עם איך לבדוק אותה — לפני שנוגעים בקוד. בצעו RAVEN review ממוקד לזיהוי הנחות, אימות והשפעות השינוי.

עבודה עם IBM Bob
Ask

Evidence before fix — ניתוח בעזרת RAVEN.

Prompt לדוגמה

Bug: [describe]. Run a RAVEN debugging review focused on: Assumptions (what code paths or properties did we assume?), Verification (how to prove the fix works with logs or test cases), and Effects (what other modules or endpoints might break). No code changes yet.

למה זה עובד: Method over magic.

טעות נפוצה

לא: fix it loop.

כן: reproduce → hypothesis → test → RAVEN debugging review → fix.

מעבדה מודרכת
  1. Inject/know bug.
  2. Reproduce.
  3. Network/log evidence.
  4. Fix one thing.
  5. Regression test.
  6. הצלחה = bug מתועד עם reproduce steps, hypothesis שנבדקה, fix עם evidence ו-regression test ירוק.

תרגיל עצמאי

Debug checklist — 5 steps.

בדקו את עצמכם
Reproduce first?
תשובה לדוגמה: no reproduce = no verify fix.
Isolate?
תשובה לדוגמה: which layer — data, API, UI.
Evidence?
תשובה לדוגמה: proves hypothesis.

סיכום

  • Reproduce.
  • Hypothesis driven.
  • Evidence.
  • Regression test.
