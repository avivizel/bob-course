מצבי Ask, Plan ו-Agent

בחירת Mode לפי מטרה וסיכון

מטרת הפרק

בסוף הפרק: בחירת Mode לפי מטרה וסיכון

מבוא

שלושה מצבים — שלוש רמות סיכון. Ask = 0 שינויים. Plan = תכנון וכתיבת קבצי plan, לא קוד אפליקציה. Agent = ביצוע. הבחירה הנכונה חוסכת rollback.

מושגי מפתח

רחפו מעל שם המושג (או לחצו במסך מגע) לפירוט: מבוא, משמעות וכוונה.

Ask

מבוא

יש שאלות שאסור שיהפכו לשינוי קבצים. Ask הוא מצב חקירה.

משמעות

מצב שבו Bob קורא ומסביר בלי לערוך. סיכון מינימלי: אין שינוי בקוד.

כוונה

הכוונה: להתחיל כאן כשעוד לא ברור מה הבעיה, או כשצריך מפה לפני תכנון.

שאלות, הסבר, קריאה — בלי edit.

דוגמה: מה עושה הקובץ?
זהירות: Ask כשצריך Plan.

Plan

מבוא

בנייה בלי שרטוט מייצרת הפתעות. Plan הוא השרטוט.

משמעות

מצב שמייצר תוכנית: קבצים, שלבים, סיכונים, בדיקות — לפני עריכה.

כוונה

הכוונה: לקרוא את התוכנית כמו חוזה. לא לאשר Plan שלא מבינים.

תוכנית לפני קוד. יכול לכתוב קבצי plan (למשל plan/feature.md) — לא קוד אפליקציה.

דוגמה: רשימת קבצים + שלבים + risks
זהירות: Plan שלא קוראים.

Agent

מבוא

כאן Bob באמת משנה את העולם: קבצים, פקודות, בדיקות.

משמעות

מצב ביצוע — עריכה והרצה לפי היעד. זו רמת הסיכון הגבוהה ביותר.

כוונה

הכוונה: להפעיל Agent רק אחרי יעד, גבולות וקריטריוני קבלה ברורים — ורצוי שלב אחד.

עריכה, הרצה, שינוי.

דוגמה: מימוש שלב 1
זהירות: Agent בלי Plan/AC.

Escalation

מבוא

הטעות הנפוצה היא לקפוץ ישר ל-Agent. Escalation הוא הסולם.

משמעות

מעבר מדורג: Ask להבנה, Plan לתוכנית, Agent לביצוע ממוקד.

כוונה

הכוונה: להתאים Mode לרמת הסיכון. ככל שהשינוי גדול יותר — יותר שלבי סולם.

מעבר מדורג: Ask→Plan→Agent.

דוגמה: חקירה → תכנון → שלב 1
זהירות: קפיצה ישר ל-Agent.

Scope Creep ב-Agent

מבוא

המושג Scope Creep ב-Agent הוא אחד מאבני הבניין של הפרק.

משמעות

Agent שמתחיל בשינוי אחד ומרחיב לשינויים נוספים שלא בוקשו.

כוונה

הכוונה: להבין מתי להשתמש בו, ומה משתבש אם מתעלמים — לאשר diff בלי לקרוא — הרחבה עלולה לשבור behavior קיים.

Agent שמתחיל בשינוי אחד ומרחיב לשינויים נוספים שלא בוקשו.

דוגמה: בוקש תקן הודעת שגיאה — Bob שינה גם ה-validation logic וה-error handler
זהירות: לאשר diff בלי לקרוא — הרחבה עלולה לשבור behavior קיים.

Plan Review

מבוא

המושג Plan Review הוא אחד מאבני הבניין של הפרק.

משמעות

קריאה אנושית של Plan לפני ביצוע — לא rubber stamp.

כוונה

הכוונה: להבין מתי להשתמש בו, ומה משתבש אם מתעלמים — approve מהיר של plan ארוך — הסיכון מסתתר בפרטים.

קריאה אנושית של Plan לפני ביצוע — לא rubber stamp.

דוגמה: Plan כולל נעדכן DB — שאלו: איזה migration? Rollback?
זהירות: approve מהיר של plan ארוך — הסיכון מסתתר בפרטים.
משל מהעולם האמיתי

שלושת המצבים הם רמות סיכון גוברות: Ask לא כותב שורת קוד, Plan כותב קבצי תכנון בלבד, Agent משנה קוד אמיתי. ביצוע ב-Agent Mode ללא Plan שקול לשינוי ישיר ב-main בלי branch — מהיר, אך ללא נקודת חזרה ברורה.

שאלות לחשיבה: בחרו משימה ב-TaskFlow: הוסף סינון Done. כתבו — לפני שמבקשים מ-Bob — באיזה mode תתחילו, מה תבדקו בPlan, ומה ה-stop condition של ה-Agent. השוו לתוצאה האמיתית.

תרשים זרימה

Ask — חקירהPlan — תכנוןAgent — ביצוע
עבודה עם IBM Bob
AskPlanAgent

תמיד Escalation — לא קפיצה.

Prompt לדוגמה

Task: add a Done filter to TaskFlow. Start in Plan: files, steps, and acceptance criteria. Do not edit files.

למה זה עובד: Plan לפני Agent = roadmap.

טעות נפוצה

לא: בוקש תקן שגיאת CSS — Bob הוסיף גם refactor ל-JS ו-2 קבצים חדשים. אישרתם.

כן: הגדירו Scope ב-prompt: Edit only @public/style.css. No JS changes. — ו-review diff לפני approve.

מעבדה מודרכת
  1. בחרו משימה: הוסף סינון Done.
  2. Ask: מפו קבצים מעורבים.
  3. Plan: שלבים + AC.
  4. Agent: שלב 1 בלבד — Stop.
  5. קראו diff: האם Bob חרג מה-scope?
  6. הצלחה = גילוי מקרה אחד בו Bob ניסה לשנות מעבר למה שבוקש.

תרגיל עצמאי

בדקו את עצמכם
מתי Plan?
תשובה לדוגמה: שינוי >1 קובץ / לא ברור / סיכון.
Agent בלי Plan?
תשובה לדוגמה: שינויים לא צפויים — rollback.
Ask מספיק?
תשובה לדוגמה: כשצריך רק הבנה — לא שינוי.
Scope Creep — איך מזהים בdiff?
תשובה לדוגמה: Bob שינה קבצים שלא ציינתם ב-prompt. כל קובץ בdiff שלא הוזכר במפורש = scope creep פוטנציאלי.
Plan review — מה מחפשים?
תשובה לדוגמה: הנחות לא מוצהרות (לפי הצורך), שינויי DB ללא migration, שלבים ללא AC ברור.

  • Plan = חוזה.
  • Agent = שלבים קטנים.
