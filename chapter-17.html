Backend ו-API

שרת מקבל בקשה ומחזיר תשובה

מטרת הפרק

בסוף הפרק: שרת מקבל בקשה ומחזיר תשובה

מבוא

Backend = כללים + אבטחה. API = חוזה. Frontend לא סומך על input.

פרויקט Capstone — TaskFlow

POST/GET /api/tasks — contract + validation.

מושגי מפתח

רחפו מעל שם המושג (או לחצו במסך מגע) לפירוט: מבוא, משמעות וכוונה.

Endpoint

מבוא

השרת לא מדבר סתם. לכל פעולה יש כתובת ושיטה. זה Endpoint.

משמעות

צירוף של HTTP method ונתיב, למשל POST /api/tasks, עם משמעות עסקית אחת.

כוונה

הכוונה: לתכנן חוזה לכל endpoint לפני המימוש — לא לאסוף RPC אקראי.

path + method.

דוגמה: POST /api/tasks
זהירות: RPC soup.

Request/Response

מבוא

השיחה עם השרת היא מכתב ותשובה, לא קסם.

משמעות

Request: שיטה, כותרות, גוף. Response: קוד סטטוס וגוף JSON/HTML.

כוונה

הכוונה: להגדיר גוף וסטטוס לכל מצב — הצלחה, קלט רע, לא נמצא.

body + status.

דוגמה: 201 + {id, title}
זהירות: 200 for errors.

Validation

מבוא

הדפדפן בידי המשתמש. אפשר לשקר בטופס. השרת חייב לבדוק בעצמו.

משמעות

בדיקת קלט בצד שרת לפני שמירה: שדות חובה, אורך, טיפוס, הרשאה.

כוונה

הכוונה: לא לסמוך על validation בדפדפן כהגנה. הוא UX, לא אבטחה.

server-side always.

דוגמה: title required
זהירות: client only.

Error Codes

מבוא

להחזיר 200 עם error בגוף מבלבל לקוחות ובדיקות.

משמעות

קודי HTTP שמספרים את התוצאה: 201 נוצר, 400 קלט, 404 חסר, 500 תקלה.

כוונה

הכוונה: לבחור קוד שמתאים למשמעות, כדי שהלקוח והטסטים יתנהגו נכון.

400, 404, 500.

דוגמה: 400 invalid
זהירות: 200 + {error}.
משל מהעולם האמיתי

Validation בצד השרת קיימת כי הclient אינו מהימן — JavaScript בדפדפן ניתן לעקיפה. API שמסמוך על client validation מאפשר שליחת נתונים שרירותיים ישירות ל-DB. status codes נכונים (400, 404, 500) הם חלק מה-contract — לא פרט עיצובי.

שאלות לחשיבה: כתבו את ה-schema של POST /tasks: שדות חובה, שדות אופציונליים, ואילו status codes יוחזרו לכל תרחיש. שמרו כ-docs/api-contract.md.
