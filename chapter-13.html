מטרת הפרק

בסוף הפרק: ביקורת דרך פעולה לפני קוד

מבוא

Plan Mode = blueprint. קוראים, מערערים, מאשרים — ורק אז Agent.

פרויקט Capstone — TaskFlow

Plan ל-slice יצירת משימה — קבצים, שלבים, tests.

מושגי מפתח

רחפו מעל שם המושג (או לחצו במסך מגע) לפירוט: מבוא, משמעות וכוונה.

Plan Document

מבוא

תוכנית שחיה רק בצ'אט נעלמת. מסמך plan אפשר לבקר ולשמור.

משמעות

קובץ עם שלבים, קבצים ייגעו, בדיקות וסיכונים — למשל plan/create-task.md.

כוונה

הכוונה: לייצר ארטיפקט שניתן לאשר, לשנות, ולתת ל-Agent שלב-שלב.

קבצים, שלבים, סיכונים.

דוגמה: plan/create-task.md
זהירות: plan בראש.

Risk

מבוא

תוכנית בלי סיכונים היא אופטימיות. Risk אומר מה עלול להישבר.

משמעות

אירוע אפשרי שפוגע ביעד: מיגרציה, הרשאות, תלות חיצונית, חוסר בדיקות.

כוונה

הכוונה: לכתוב mitigation לכל סיכון — אחרת מגלים אותו באמצע Agent.

מה עלול להשתבש.

דוגמה: DB migration
זהירות: ignore risks.

Rollback Point

מבוא

לפני ש-Agent נוגע בחמישה קבצים צריך נקודת עיגון.

משמעות

commit או tag נקי לפני המימוש, כדי שאפשר יהיה לחזור במדויק.

כוונה

הכוונה: לא להתחיל Agent על working tree מלוכלך. קודם נקודה יציבה.

commit לפני Agent.

דוגמה: git tag pre-slice-1
זהירות: no checkpoint.

RAVEN Review

מבוא

המושג RAVEN Review הוא אחד מאבני הבניין של הפרק.

משמעות

מסגרת לביקורת plan לפני Agent: Requirements / Assumptions / Verification / Effects / No-go.

כוונה

הכוונה: להבין מתי להשתמש בו, ומה משתבש אם מתעלמים — auto-approve plan.

מסגרת לביקורת plan לפני Agent: Requirements / Assumptions / Verification / Effects / No-go.

דוגמה: האם הplan מכסה את ה-AC? אילו הנחות Bob הוסיף? איך כל שלב ייבדק?
זהירות: auto-approve plan.
משל מהעולם האמיתי

Plan שנכתב לפני קוד חושף הנחות — כלומר החלקים שBob ממלא לבד מבלי לדעת. Plan שנכתב אחרי קוד הוא תיעוד, לא תכנון. RAVEN review מחפש את ה-נעדכן לפי הצורך שבplan — זה תמיד הגיאה שתעלה בproblems.

שאלות לחשיבה: פתחו plan/create-task.md ו-RAVEN אותו: זהו הנחה אחת לא מוצהרת וכתבו כיצד לבדוק אותה לפני שמתחילים לכתוב קוד.

עבודה עם IBM Bob
Plan

Plan → RAVEN review → Agent.

Prompt לדוגמה

Review this plan using RAVEN:

R — Requirements:
List the explicit requirements.

A — Assumptions:
List every assumption not guaranteed by the repository or the request.

V — Verification:
For each requested outcome, define evidence that proves it works.

E — Effects:
List files, dependencies, APIs, data, security boundaries and users that may be affected.

N — No-go:
List components or behavior that must not change.

Do not implement anything yet.

למה זה עובד: RAVEN הופך Plan לביקורת שיטתית לפני אישור.

טעות נפוצה

לא: Agent בלי plan מאושר.

כן: Plan file → RAVEN review → approve → step 1.

RAVEN Review

לפני שמאשרים Plan:

  • Requirements — מה בדיוק נדרש?
  • Assumptions — מה Bob מניח שלא נאמר?
  • Verification — איך נדע שהשינוי הצליח?
  • Effects — אילו קבצים, שירותים, APIs, נתונים או משתמשים מושפעים?
  • No-go — מה אסור להשתנות?

מעבדה מודרכת
  1. Plan Mode → create task.
  2. RAVEN: בדקו Requirements, Assumptions, Verification, Effects, No-go.
  3. Approve.
  4. שמרו plan/.
  5. הצלחה = קובץ plan/create-task.md ב-repo, עם RAVEN pass ולפחות הנחה אחת שזוהתה ותוקנה.
