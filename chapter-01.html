מהי מערכת תוכנה?

להבין ממה בנויה תוכנה ואיך מידע נע בין החלקים שלה

מטרת הפרק

בסוף הפרק: להבין ממה בנויה תוכנה ואיך מידע נע בין החלקים שלה

מבוא

כשאנחנו לוחצים על כפתור באפליקציה, נראה רק מסך אחד. מאחורי הקלעים פועלים כמה שכבות: ממשק, שרת, מסד נתונים — וכל אחת עם תפקיד שונה. בפרק זה נבנה תמונה מנטלית שתלווה אתכם בכל הקורס.

מושגי מפתח

רחפו מעל שם המושג (או לחצו במסך מגע) לפירוט: מבוא, משמעות וכוונה.

קלט, עיבוד ופלט

מבוא

כל תוכנה חיה במחזור: היא מקבלת משהו, מחליטה מה לעשות, ומחזירה תוצאה. בלי לפרק את המחזור הזה קשה להבין באגים.

משמעות

קלט הוא הנתונים שנכנסים (לחיצה, טופס, קובץ). עיבוד הוא הכללים והחישוב. פלט הוא מה שהמשתמש או מערכת אחרת רואים.

כוונה

הכוונה: לזהות בכל תכונה איפה הקלט, איפה ההחלטה ואיפה הפלט — כדי לדעת מה לבדוק ומה לבקש מ-Bob.

קלט = מה שהמשתמש מוסר. עיבוד = החישוב או ההחלטה. פלט = התוצאה שחוזרת.

דוגמה: בטופס הרשמה: קלט = שם ואימייל, עיבוד = בדיקת תקינות, פלט = הודעת הצלחה.
זהירות: אם מדלגים על שלב — קשה לדעת איפה נשבר.

Frontend

מבוא

המשתמש לא רואה שרת או מסד נתונים. הוא רואה מסך. Frontend הוא השכבה הזו.

משמעות

HTML, CSS ו-JavaScript שמציגים רשימות, טפסים וכפתורים בדפדפן או בטלפון, ומגיבים לפעולות המשתמש.

כוונה

הכוונה: להפריד בין מה שרואים לבין מה שנשמר. Frontend מציג; הוא לא מקור האמת של המידע העסקי.

החלק שהמשתמש רואה: כפתורים, טפסים, רשימות.

דוגמה: דף רשימת משימות ב-TaskFlow.
זהירות: Frontend לא שומר מידע לצמיתות לבד.

Backend ו-API

מבוא

מאחורי המסך צריך מישהו שמגן על כללים: מי רשאי, מה חוקי, מה נשמר. זה השרת.

משמעות

Backend הוא הקוד שרץ בשרת. API הוא החוזה: כתובת, שיטה, גוף הבקשה והתשובה. Frontend מדבר עם השרת רק דרך ה-API.

כוונה

הכוונה: לא לבלבל API (דרך גישה) עם Database (אחסון). API מבקש; DB שומר.

השרת מבצע כללים עסקיים; ה-API הוא חוזה התקשורת.

דוגמה: POST /tasks יוצר משימה חדשה.
זהירות: לבלבל בין API (דרך גישה) לבין DB (אחסון).

Database

מבוא

אם סוגרים את הדפדפן והמידע נעלם — הוא לא היה במסד נתונים. DB הוא הזיכרון לטווח ארוך.

משמעות

מאגר מאורגן (טבלאות, שורות, מזהים) שמחזיק מידע גם אחרי הפעלה מחדש, וניתן לשאילתה.

כוונה

הכוונה: להחליט במודע מה חייב להישמר (משימות, משתמשים) ומה יכול להישאר זמני במסך.

מאגר מידע ששרד אחרי סגירת האפליקציה.

דוגמה: טבלת tasks עם id, title, status.
זהירות: לשמור מידע רק בזיכרון הדפדפן.

Request / Response

מבוא

המושג Request / Response הוא אחד מאבני הבניין של הפרק.

משמעות

הלקוח שולח request, השרת מחזיר response. שניהם מכילים headers + body.

כוונה

הכוונה: להבין מתי להשתמש בו, ומה משתבש אם מתעלמים — לטפל רק ב-happy path ולהתעלם מ-4xx/5xx.

הלקוח שולח request, השרת מחזיר response. שניהם מכילים headers + body.

דוגמה: GET /tasks → 200 OK + [{id:1, title:'...'}]
זהירות: לטפל רק ב-happy path ולהתעלם מ-4xx/5xx.

Stateless

מבוא

המושג Stateless הוא אחד מאבני הבניין של הפרק.

משמעות

כל request עומד בפני עצמו — השרת לא זוכר את הקודם. State נשמר ב-DB או session.

כוונה

הכוונה: להבין מתי להשתמש בו, ומה משתבש אם מתעלמים — לאחסן state ב-memory של השרת — נאבד בהפעלה מחדש.

כל request עומד בפני עצמו — השרת לא זוכר את הקודם. State נשמר ב-DB או session.

דוגמה: API שמקבל token בכל בקשה — לא מסתמך על 'זוכרים אותך'.
זהירות: לאחסן state ב-memory של השרת — נאבד בהפעלה מחדש.
משל מהעולם האמיתי

כל שכבה עושה בדיוק דבר אחד: Frontend מציג ואוסף, Backend מחליט ומאמת, Database שומר. כשמשהו נשבר — הבדלת האחריות מצביעה מיד על השכבה הכשולה. מערכות ללא הפרדה כזו הופכות ל-big ball of mud — שגיאה אחת משפיעה על הכל.

שאלות לחשיבה: פתחו את TaskFlow ב-Ask. בקשו מ-Bob לצייר את מסלול הנתונים מ-לחיצת כפתור הוספה עד שמירה ב-DB — לא קוד, רק flow. בדקו: האם כל שכבה מופיעה? האם ה-flow מתאים ל-diagram שבפרק?

עבודה עם IBM Bob
Ask

בפרק פתיחה עובדים ב-Ask בלבד — Bob מסביר, לא נוגע בקוד.

Prompt לדוגמה

In Ask mode: analyze @src. Explain Frontend, Backend, and DB, and the path from clicking Add Task until it appears on screen. Do not change files.

למה זה עובד: מגדירה Mode, תחום (@), תוצר מילולי וגבול ברור.

טעות נפוצה

לא: שואלים מה עושה הקוד? ו-Bob עונה נכון אבל התשובה לא מסייעת — כי השאלה לא מוגדרת.

כן: הסבר את המסלול מ-submit הטופס עד התגובה מה-DB — שכבה אחת בכל פעם.

מעבדה מודרכת
  1. פתחו TaskFlow ב-Ask.
  2. בקשו מ-Bob: זהה קובץ UI, קובץ API, וקובץ DB.
  3. ציירו flow diagram מהלחיצה עד ה-DB.
  4. בקשו מ-Bob לתאר מה קורה ב-error case — שגיאת validation.
  5. תעדו: האם ה-flow הגיוני? האם גיליתם שכבה שציפיתם לה במקום אחר?
  6. הצלחה = יש לכם diagram מדויק עם 4 שכבות וזיהוי ברור של קובץ כל שכבה.

תרגיל עצמאי

בחרו פעולה אחת מאפליקציה שאתם מכירים (למשל חיפוש) ופרקו אותה ל-4 שכבות.

בדקו את עצמכם
מה ההבדל בין Frontend ל-Backend?
תשובה לדוגמה: Frontend מציג ואוסף קלט; Backend מחיל כללים ומדבר עם DB. Frontend לא אמור לסמוך על נתונים מהדפדפן.
למה API אינו מסד נתונים?
תשובה לדוגמה: API הוא ממשק — דרך לבקש פעולות. DB הוא המקום שבו הנתונים חיים. API קורא/כותב ל-DB.
מה קורה למידע ששמור רק בזיכרון?
תשובה לדוגמה: נמחק ברענון/סגירה. לכן מידע עסקי חייב ב-DB או אחסון מתאים.
מה זה Stateless API ולמה זה חשוב?
תשובה לדוגמה: כל request עצמאי — השרת לא מסתמך על מה ששלחת קודם. זה מאפשר scale horizontal ומונע באגים של state פג-תוקף.
API מחזיר 200 על כל request. מה הבעיה?
תשובה לדוגמה: מחליא — הלקוח לא יכול לדעת אם הפעולה הצליחה. 400/404/500 הם חלק מה-contract ומאפשרים טיפול שגיאות תקין.

סיכום

  • מערכת = שכבות עם תפקידים ברורים.
  • מסלול מידע אחד עדיף על להבין הכל.
  • Ask Mode מתאים לחקירה לפני שינוי.
  • ראיה = diagram או הסבר שניתן לבדוק.
