כיצד IBM Bob זוכר את הפרויקט שלך

מדריך מעשי ליצירת הקשר מתמשך ב־IBM Bob באמצעות AGENTS.md, כללים מותאמים וקבצי ידע של הפרויקט.

כל שיחה חדשה עם מודל שפה מתחילה עם חלון הקשר חדש. IBM Bob אינו "זוכר" אוטומטית את כל מה שנאמר בשיחות קודמות. כדי לשמר ידע בין שיחות, יש להכניס את המידע החשוב לקבצים שבוב טוען מחדש או יכול לקרוא מתוך סביבת העבודה.

Bob מספק שלושה מנגנונים משלימים:

  1. קובצי AGENTS.md — הקשר קבוע על הפרויקט, הארכיטקטורה, הפקודות והכללים.
  2. Custom Rules — הוראות כלליות או תלויות־מצב תחת .bob/rules/ ו־.bob/rules-{mode}/.
  3. קובצי ידע מנוהלים בפרויקט — החלטות, לקחים, סטטוס ותיעוד שבוב קורא לפי דרישה או לפי הוראה ב־AGENTS.md.

CGCA: איך Prompt בונה הקשר למשימה

תבנית הקורס ל־Prompt: Context, Goal, Constraints, Acceptance. זה הקשר למשימה. הוא לא מחליף AGENTS.md.

Context: @src/tasks
Goal: Add All / Open / Done filter
Constraints: vanilla JS, no new libraries
AC: all three states work + a unit test
Show a Plan before editing.
כלל אצבע אם תצטרכו את אותו משפט גם מחר בשיחה חדשה — הוא שייך לקובץ. אם הוא נכון רק לפיצ'ר הזה — הוא שייך ל־Prompt ול־@.

הנחות חייבות להיכתב

כשחסר מידע Bob משלים פער ומתקדם. בקורס זו הנחה — לא עובדה. לפני Agent דרשו:

Before any action: write what you understood, list assumptions, ask blocking questions, and propose how to verify. Do not change code.

הנחה יציבה (למשל סטטוס משימה הוא רק open או done) עוברת ל־AGENTS.md אחרי אישור אנושי. הנחה חד־פעמית נשארת בשיחה.

TaskFlow כמקרה מבחן

פרויקט ה־Capstone של הקורס הוא TaskFlow — מנהל משימות צוותי ב־HTML/CSS/JS, Node.js, Express ו־SQLite. כך מחלקים הקשר:

  • ב־AGENTS.md: stack, פקודות npm run dev | test | build, כלל עסקי של סטטוס, חובת בדיקות לפני Done.
  • ב־Prompt עם @: הקובץ של ה־slice הנוכחי, למשל @plan/create-task.md ו־@public/.
  • ב־memory: ADR על auth בסיסי, מגבלות ידועות, Runbook למסירה.

Ask → Plan → Agent נשאר הסולם: ב־Ask קוראים הקשר; ב־Plan כותבים תוכנית; ב־Agent מממשים שלב אחד מתוך הקבצים שצוינו.

פורמט מומלץ להחלטה

## ADR-012 — Preserve raw extraction values

- Date: 2026-08-24
- Status: Accepted
- Context: Normalization can conceal extraction errors.
- Decision: Store both `raw_value` and `normalized_value`.
- Rejected alternative: Store only normalized values.
- Consequences: More storage and schema complexity; full auditability.
- Evidence: Link to issue, test, or approved design.

פורמט מומלץ ללקח

## PDF text extraction may preserve visual order incorrectly

- Symptom: Values are associated with the wrong label.
- Confirmed cause: PDF drawing order differs from reading order.
- Correct approach: Use layout coordinates and confidence checks.
- Verification: Run fixtures `tests/payslips/layout_cases/`.
- Do not: Infer a field solely from nearby plain text.

מגדירים את המוצר לפני הקוד

לפני ששואלים כיצד לממש, מנסחים מה צריך לקרות. תבנית Mini‑PRD קצרה מספיקה לרוב המשימות:

# שם התכונה

## הבעיה
משתמש אינו יודע אם העלאת PDF התקבלה.

## המשתמש
עובד שכר שאינו טכני.

## בתוך התחום
- PDF יחיד עד 10MB
- חיווי העלאה וסטטוס עיבוד

## מחוץ לתחום
- OCR
- שינוי מערכת ההרשאות

## קריטריוני קבלה
Given קובץ PDF תקין
When המשתמש מעלה אותו
Then מוצגים מזהה, סטטוס וזמן קבלה

## מגבלות
אין לשמור תוכן מסמך בלוגים; ה־API הקיים נשאר תואם.
גישה שגויהגישה נכונה
"בנה מסך העלאה יפה ומקצועי.""צור העלאת PDF יחיד עד 10MB, progress, validation והודעה נגישה. אל תשנה API."

מבקרים את התוכנית לפני המימוש

בדוק תוכנית באמצעות RAVEN:

  • Requirements: האם היא מכסה את כל הדרישות ורק אותן?
  • Assumptions: אילו הנחות Bob הוסיף והאם הן נכונות?
  • Verification: כיצד כל שלב ייבדק?
  • Effects: מה ההשפעה על API, נתונים, אבטחה וביצועים?
  • No‑go: היכן נדרש אישור אנושי?
ניסוח חשודניסוח ניתן לאישור
"נעדכן קבצים לפי הצורך ונוסיף טיפול שגיאות מתאים.""נעדכן את documents.controller.ts: 404 למזהה חסר, 503 לכשל repository ושתי בדיקות."

כאשר קיימת החלטה יקרה — schema, consistency, latency, ספרייה חדשה או API ציבורי — בקש טבלת חלופות והמלצה מנומקת. האדם מחליט.

מימוש בפרוסות קטנות

פרוסה אנכית היא חתיכת ערך קטנה שעוברת דרך השכבות הנחוצות ומסתיימת בתוצאה עובדת. היא עדיפה על שינוי רחב שאי אפשר לבדוק עד סופו.

עבוד ב־Agent mode וממש רק את שלב 1 המאושר.
לפני עריכה: הצג את הקבצים שתשנה ואשר שאין שינוי dependency או schema.
לאחר עריכה: הרץ unit tests, lint ו־typecheck הרלוונטיים.
הצג סיכום diff, פקודות ותוצאות. עצור לפני שלב 2.
מלכודת "רק עוד תיקון"אם Bob שינה 20 קבצים כדי לתקן כפתור, אל תנסה להציל את הכיוון בעשר הודעות. השתמש ב־rollback, צמצם Scope והתחל מחדש מנקודת בסיס.

בדיקות, ניפוי ואבטחה

"הקוד נכתב" אינו Done. נדרשות ראיות: lint/typecheck, בדיקות unit, integration או end‑to‑end לפי הסיכון, וסקירת diff אנושית.

ניפוי תקלה מתודי

  1. שחזר את התקלה באופן עקבי.
  2. אסוף stack trace, logs וקלט מינימלי.
  3. בקש 2–3 השערות ואת הראיה שמבדילה ביניהן.
  4. בצע ניסוי קטן שמשנה משתנה אחד.
  5. לאחר תיקון, הוסף regression test.
שגוינכון
"יש AssertionError. תקן.""שחזר בפקודה X, קרא @terminal, הצג השערות ואל תשנה קוד לפני ראיה."

בדיקת אבטחה בסיסית

  • אין secrets או PII בקוד, prompt, log או fixture.
  • קלט נבדק בגבול המערכת.
  • Authorization נאכף בשרת ולא רק ב־UI.
  • שגיאות חיצוניות אינן חושפות פרטים פנימיים.
  • Dependencies חדשות מוצדקות ונסרקות.
  • אין בניית query, command או template מחיבור מחרוזות מסוכן.
Rules אינם Security Controlהנחיה מסייעת, אך אכיפה נעשית באמצעות permissions, .bobignore, hooks, CI, secret scanning וביקורת אנושית.

Git, סקירה ותיעוד

  • קרא את git diff בעצמך.
  • ודא שאין קבצים לא קשורים, secrets או generated files.
  • בדוק שינויי dependencies ו־lock files.
  • הרץ את סט הבדיקות המוסכם.
  • צור commit קטן שמייצג שינוי לוגי אחד.

בקש ראיות ולא הצהרות: במקום "הכול עובד", דרוש רשימת פקודות, תוצאות ו־exit code; במקום "לא שברתי API", דרוש contract diff ובדיקות.

סיכום

Bob אינו זקוק ל"זיכרון אנושי" כדי לעבוד בעקביות; הוא זקוק למקורות אמת קצרים, מדורגים ומתוחזקים:

  • הקשר בשיחה (@ + Prompt) מסביר מה רלוונטי למשימה הזו.
  • AGENTS.md מסביר מהו הפרויקט וכיצד עובדים בו.
  • Custom Rules מגדירים כיצד Bob צריך להתנהג.
  • קובצי ידע מנוהלים שומרים החלטות, לקחים וסטטוס שאינם נגזרים מהקוד.
  • CI, הרשאות ו־hooks אוכפים מה שאסור להשאיר לשיקול דעת המודל.

כך בונים זיכרון פרויקט שקוף, ניתן לביקורת, משותף לצוות ואינו תלוי בשיחה קודמת.
